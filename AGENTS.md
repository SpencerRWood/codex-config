# Shared Codex Guidance

- Prefer short, bounded execution phases over long-running sessions.
- At logical objective, repository, or deployment boundaries, create a concise handoff and start a fresh session when practical.
- Prefer deterministic helpers with bounded structured output over repeated exploratory commands or large raw logs.
- Keep full diagnostic output on disk and return only the summary, failures, relevant identifiers, and log path.
- Do not repeatedly rerun expensive validation unless a change or failure requires it.
- Read only the files and documentation needed for the current task.
- Prefer existing repository commands, scripts, and skills over recreating equivalent logic ad hoc.
- Do not add or retain legacy configuration loaders, compatibility aliases, forwarding wrappers, or deprecated-setting fallbacks. Migrate first-party callers to the supported interface and remove superseded paths; report a missing requirement directly instead of silently consulting old configuration.
- Use Wood Tools first for supported OpenProject, repository, CI, delivery, verification, and hierarchy operations. Read `wood contract --json` once for the selected executable, consume bounded JSON, and reuse returned facts and file paths during the same workflow.
- Run plain `wood` commands from the current task repository using the globally installed executable; in a Wood Tools checkout under review, use `uv run --active --frozen wood`. Require Wood Tools v0.19.2 or later for repository-owned OpenProject context without legacy fallback. Resolve `project_id` and `initiative_id` from the current Git root's `[tool.wood.openproject]` in `pyproject.toml`; supported explicit CLI selectors override the context they select. Do not use `OPENPROJECT_PROJECT_ID` or `OPENPROJECT_INITIATIVE_ID` as overrides or fallbacks. When required repository context is missing, configure the mapping or use a supported explicit CLI selector.
- Only `OPENPROJECT_URL` and `OPENPROJECT_API_TOKEN` are globally required OpenProject runtime values. The URL is non-secret global configuration. Keep the token Infisical-backed and inject it only into the command process; never persist it in `.env`, `pyproject.toml`, configuration files, logs, diagnostics, or generated artifacts. Project discovery works with URL/token alone; do not require repository IDs for commands that do not need them.
- Use `wood delivery status <id> --json` for a point-in-time delivery briefing. Reuse `observed_at`, `merged_revision`, the exact `release_run` ID/attempt, and bounded `release_jobs` diagnostics. Follow its `delivery_stage`, `blocker`, and `next_action`; envelope success means the query completed, not that delivery passed. Refresh after a relevant mutation or state change, not in a watch loop. Release-job success does not attest to an image digest, deployment, or runtime health.
- When delivery status supplies an exact diagnostic command, reuse its run, attempt, and job IDs; retain full diagnostic output on disk. Truncated job/step lists require the linked authority for omitted details. Distinguish an outdated installed Wood executable from missing functionality in the current repository before choosing a fallback; use the verified executable for the workflow.
- Use `wood repo verify --json` for declared repository-owned application checks and pass its saved record with `wood story evidence --verification`. Wood Tools owns execution and normalized results; the repository owns application semantics and retry safety.
- Use `wood hierarchy plan --json` and `wood hierarchy ensure --apply --plan-hash <reviewed-hash> --json` for authorized hierarchy provisioning. Preserve verified mappings; reject ambiguity and stale plans instead of guessing or bypassing them.
- Use direct GitHub/OpenProject/infrastructure tools only after identifying a capability that Wood Tools lacks, an unsupported repository workflow, or a focused diagnostic gap; explain the fallback once. PR creation/merge remains a GitHub operation. Do not bypass Wood Tools merely because an API is available.
- Use `wood epic list/get` and `wood release list/get` for supported live OpenProject inspection, with `--json` and project/status/offset options as needed. Release inspection refers to OpenProject planning versions.
- Edit repository code and tests directly with patch/edit tools. Do not create temporary Python file-writing helpers for routine changes. Check the supported command surface before using custom API scripts, and explain any unsupported-operation fallback.
- For OpenProject Story work, use the `openproject-development-workflow` skill. Prefer supported `wood` commands with `--json` and available filters. Use direct tools or custom scripts only for unsupported operations or focused diagnosis, and explain the fallback.
- A Story implementation request authorizes in-scope inspection, dependency verification, implementation, tests, required validation, failure fixes, evidence preparation, and proposed commit/PR summaries without intermediate approval prompts. The first normal approval boundary is immediately before commit/push/PR creation; present the skill's concise review and stop for approval. After approval, continue its standard delivery and closure workflow. Scope expansion and separately required tool/runtime approvals remain outside this authorization.
- Reuse the validation record and generated delivery inputs returned by Wood Tools. Use `wood story evidence` for supported repository workflows instead of manually assembling routine evidence JSON or implementation-update Markdown; follow the workflow skill for verification and posting.
- Reuse one verified delivery snapshot in briefings and handoffs, including observation time, revisions, record/log paths, applicable verification, limitations, and the next exact action. Keep deterministic evidence separate from narrative; an unavailable or stale result is not a passed check.
- Keep project-specific workflows, architecture, and implementation guidance in repository-local AGENTS files or task-specific skills.
- Before external, destructive, production, or irreversible actions, require explicit confirmation unless the action is already covered by task authorization or an approved workflow. Apply the Story skill's autonomous implementation and commit-boundary policy to Story work; it does not authorize unrelated destructive operations, secret disclosure, or bypassing safety controls.
- After completing an audit, use the shared `audit-findings-log` skill to save its findings in Google Drive `Logs/`. This standing workflow is authorized by the user; a specific audit request that forbids Drive writes takes precedence.
- When finishing a task, report the verified state, validation performed, blockers, and the next exact action.
